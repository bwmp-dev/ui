## The loop

```bash
pnpm changeset          # describe the change
pnpm version-packages   # apply it: bump versions, write changelogs
pnpm release            # build and publish
```

## Describing a change

Run `pnpm changeset` alongside the work, not at release time. It asks which
packages changed and how, and writes a markdown file to `.changeset/`.

```md
---
'@bwmp-dev/ui': minor
'@bwmp-dev/tokens': patch
---

Add SplitPane, and a --row-h token for table rows.
```

The summary ends up in the changelog and is the first thing a reader sees when
deciding whether an upgrade matters to them. Write it for that reader.

Which bump:

| Bump    | For                                               |
| ------- | ------------------------------------------------- |
| `patch` | A fix, or anything invisible from outside         |
| `minor` | A new component, prop, token or hook              |
| `major` | A removal, a rename, or changed default behaviour |

Changed _visual_ defaults deserve a `minor` and an explicit note. They are not a
breaking API change, but they will show up in someone's screenshots.

## Versioning

Packages version independently. A change to `@bwmp-dev/ui` does not bump
`@bwmp-dev/hooks`, so a project can upgrade one without auditing the other.

Changesets bumps dependants automatically: a `minor` on `@bwmp-dev/tokens` gives
`@bwmp-dev/ui` a `patch`, because its dependency range moved.

`@bwmp-dev/eslint-config` and `@bwmp-dev/tsconfig` change rarely and version
on their own, which matters — a lint rule change should never force a component
library upgrade.

## Releasing

`pnpm version-packages` consumes the changeset files, bumps versions, writes
`CHANGELOG.md` and updates the lockfile. Review that commit: it is the last
point where a wrong bump is cheap to fix.

`pnpm release` builds every package and publishes. It builds first, so a package
that does not compile is never published.

## Registry

Nothing in the architecture is tied to one. The packages are scoped
(`@bwmp-dev/*`), publish with `access: restricted`, and can go to npm, GitHub
Packages, or anything else, by pointing `.npmrc` at it:

```ini
@bwmp-dev:registry=https://npm.pkg.github.com
```

Adding a registry later is a configuration change, not a refactor.

## Before publishing for the first time

- Confirm that the publishing account can publish under the `@bwmp-dev` scope.
- Set `publishConfig.access` to `public` if that is the intent — the default
  here is `restricted`, which is the safe way round.
- Check `files` in each `package.json`. The packages ship `src` alongside
  `dist`, deliberately: the Tailwind `@source` directive scans it, and it makes
  debugging a published package possible.
- `pnpm publish --dry-run` and read the file list.

## The generator

`@bwmp-dev/create-stack` bundles the templates at pack time, so an installed CLI
does not need the monorepo. `prepack` copies them in and freezes the versions
it would otherwise read from the workspace, which is why a generated project
gets real ranges rather than `workspace:*`.
